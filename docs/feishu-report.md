## 2. 总体策略:为什么这样设计

### 2.1 双镜头原则(本评测最核心的设计)

同一个模型,走厂商自己的 API 和走 Reactor 托管平台,测出来是**两个不同的东西**:

- **Lens P(产品镜头)**= 官方 API:回答"**客户买到手是什么体验**"。这是报告的主镜头。
- **Lens M(平台镜头)**= Reactor 统一平台:基础设施完全一致,**只比模型本身**。LingBot 和 Happy Oyster 只有这一条通道。

**硬规则:两个镜头的数字永远不进同一张表。** 这条在代码层强制执行(混用直接抛错,物理上无法生成违规表格)。

**桥接测量**:Xmax 恰好双通道可达 —— 同一模型、同一素材、同一分辨率走两条路,差值就是**平台开销的实测值**。这是把 Lens M 数字"翻译"回真实世界的唯一钥匙,也是本周最重要的单项测量(结果见 §5.2)。

### 2.2 时延:一个词,三种测量(按类别分别定义)

"延迟"在三类产品里根本不是同一个物理量,混在一起比较是伪科学:

| 类别 | 定义 | 通俗解释 | 测量仪器 |
|---|---|---|---|
| V2V | 输入帧 → 对应输出帧 | **你动一下,屏幕里的"你"多久跟上** | 光脉冲互相关(素材中埋入不规则闪光,输出中找回) |
| 生成 | 指令发出 → 画面首次可见偏离 | 你说"变成夜晚",画面多久开始变 | 相对自身基线的偏离检测 |
| 数字人 | 音频起始 → 嘴唇起动 | 声音出来,嘴多久动 | 音视频起始点配对 |

三种区间在代码层互斥 —— 聚合函数拒绝混算,报表拒绝混排。

**为什么用闪光而不是烧录时间码**:V2V 模型会把画面整体重绘("变成油画"),烧进去的数字/条码会被涂掉;但**光的瞬变在任何风格化下仍是瞬变**。实验证实:经 γ=2.2、动态范围压到 35% 的极端风格化,闪光法仍能把已知延迟找回到 1 帧以内。闪光间隔做了**不规则抖动**(700–1300ms),防止周期混叠(等间隔闪光会让算法锁到错一个整周期的假峰,实测抓到过一次 +1000ms 的假读数并因此改进)。

**两个衍生指标**(用户体验直接相关):
- **时延漂移**(ms/分钟):画面里的角色是否越来越落后?60 秒长镜头下 300ms 漂到 900ms 与稳定 300ms 是完全不同的产品;
- **多久崩**(生存分析):理想世界里视频永不中断,所以"活到测试上限的比例 + 中位存活时间"用 Kaplan-Meier 生存曲线统计 —— 活满全场的场次算"至少活了 X 秒"而不是丢弃,否则会把最稳定的产品算得最差。

### 2.3 三层评分体系(相互隔离,不许污染)

**第一层:计算指标**(覆盖 100% 素材,无人工)
LPIPS 时序闪烁 · 光流端点误差 · ArcFace 人脸相似度(**看斜率不看均值** —— 从 0.9 漂到 0.6 的模型均值可能还不错,但已经"换脸"了)· CLIP 提示契合度 · SyncNet 口型同步 · 眨眼频率与间隔方差。
**锚点计分法**:所有指标不用论文里的绝对阈值(不同内容间不可迁移),而是相对两个锚点定位 —— 锚点0(未处理原片=管线噪声地板)与锚点R(真人实拍参照)。
**地位:辅助证据。与人评冲突时人评说了算,且冲突本身作为发现报告。**

**第二层:盲评人评**(分层抽样)
- ≥3 名评委,含 1 名非技术人员;
- 素材去品牌、**统一转码到同一分辨率**(输出分辨率既泄露产品身份、又会被评委当"构图好"误计分;分辨率/帧率作为产品卡上的"声明事实"单独呈现,由读者自行权衡);
- 文件名 HMAC 加密、映射表存在评审目录之外、上线前全目录扫描防泄露(评委是同事,总会有人想猜);
- 每对比较**左右随机**(独立随机流、逐对记录,事后可统计"左侧偏好"—— 若存在,那是工具的发现,先于任何产品结论报告);
- 双画面**同步播放、单一进度条**(两个独立播放器会让评委比较不同时刻,时序连贯性评分变噪声);
- 每位评委埋**隐藏重复片段**(测其自身一致性,偏差>1分则标记);
- 单场 45 分钟硬上限(疲劳评分是噪声,由记录时钟强制);
- **Krippendorff's α 一致性门槛**:≥0.80 正常陈述;0.67–0.80 谨慎陈述;**<0.67 = "有争议",代码禁止输出排名**,"三位受训评委无法达成一致"本身就是有价值的结论。

**第三层:可靠性**(与质量完全隔离)
每次运行六分类:成功 S / 降级 D / 失败 F / 超时 T / 拒绝 R / 环境问题 E。
- 质量只在成功场次上评(失败的场次没有质量可言,但绝不许把失败藏进质量分);
- 拒绝(内容政策)单独统计,是政策特征不是缺陷;
- **一切比率带 Wilson 95% 置信区间,区间不重叠才允许说"谁更可靠"**。N=300 才能把 5% 和 0.5% 分开 —— 这就是通宵自动化的意义;
- 环境问题(E)只在有**正面证据**时自动判定(网络探针失败、虚拟摄像头冻结、VPN 漂移、账户欠费),模糊情况默认算产品失败、进入人工复核队列 —— 反向默认会让模糊性悄悄美化每个产品的数字。

### 2.4 公平性与防偏差机制(全部代码强制,不靠自觉)

| 机制 | 防什么 |
|---|---|
| 评分表预注册冻结(维度/权重/锚点描述,含日期) | "你就是喜欢那个产品"的指控;改动必须走修订日志,否则 CI 失败 |
| 三种使用场景权重(直播/离线/交互)**全部计算并公布** | 权重挑选嫌疑;若排名随场景翻转,翻转本身就是给读者的决策规则 |
| 权重 ±10% 扰动敏感性检验 | 排名是否脆弱;脆弱就如实报告并点名关键权重 |
| 分差 <0.3 判平局 | 过度解读噪声 |
| 单一母片 → 确定性降采样(内容寻址 recipe_id 逐 run 记录;禁止放大) | "每家 SDK 自己内部缩放"这种事后无法重建的混淆 |
| 交互契约分组:文本驱动 vs 键鼠驱动不互相排名 | 拿 G1–G7 文本题去考一个键鼠操控的世界模型,打 1 分是测量错误不是产品发现(实测:LingBot 支持文本指令,与 Happy Oyster 同组可比) |
| 服务端版本逐 run 记录 | 厂商中途升级污染对比(**已真实捕获一次** Reactor 升级,见 §6) |
| 网络指纹每轮前后探测,漂移判 E | VPN/隧道抖动冒充产品行为(**已真实抓到并因此重测**,见 §6) |
| 轮次制排队:所有产品做完第 n 轮才进第 n+1 轮 | 快败产品抢跑导致中断时样本失衡;凌晨 4 点断电剩下的也是均衡可比样本 |
| 预算闸:先预留最大成本再执行,硬顶熔断 | 通宵挂机烧穿预算(**账户欠费已真实发生一次**,系统按设计快速失败,见 §6) |
| 重试只限环境问题;产品失败(F/T/R)**永不重试** | 把失败洗成成功 —— 本评测里最危险的单一错误 |
| 逐环节人工目检抽样并留痕(eyeball 日志) | 所有数字自洽但画面明显不对 —— 测试永远抓不到的那类失败 |

## 3. 测量仪器与标定(为什么数字可信)

- **合成录屏法**(用于封闭产品,如 Xmax 官方网页端):输入画面与输出画面在**同一渲染帧内**拼合录制 —— 同一录制帧里的内容必然同屏同刻,时延从画面内容里提取,不依赖任何浏览器时间戳。链路自身延迟经回环标定(33.3ms,恰好 2 帧)并扣除;**链路抖动实测 ±1.9ms**(8 次回环,不规则闪光法)。规则:合成法数字必须携带实测抖动界,且**不与 SDK 直采数字同表**(代码强制)。
- **SDK 直采法**(Reactor/Decart 程序化通道):帧到达即打单调时钟戳,解析/落盘之前;所有派生量(TTFF、到达帧率、卡顿、时延)出自同一规范化事件流。
- 采集文件逐个验证恒定帧率(CFR),变帧率判环境问题重跑 —— 变帧率会悄悄毁掉一切按帧号计算的指标。
- 两大提供商的帧交付均为**突发式**(约 3–4 帧一组),已计入 TTFF/卡顿判读口径。

## 4. 接入工程实录(简述)

- **Decart**:官方 API,鉴权为 URL 参数;实际媒体面是 WebRTC(官方文档有完整信令协议);上行必须强制 H.264(软件 VP8 编不动 720p30,曾导致服务端"喂不饱"静默停流 —— 用发送端统计定位);客户端令牌过期**不断流**(官方文档确认),长镜头无需重连逻辑。
- **Reactor**:API key 先换短期 JWT 再用;模型目录**不含未公开模型**(Happy Oyster 需直接建会话验证);版本号从会话响应取(目录取不到未公开模型);媒体 WebRTC,经官方 Python SDK。
- **Xmax**:中国区主站鉴权,临时密钥机制用于浏览器端;媒体面为火山引擎 RTC 房间(模型作为房间内 bot)。
- **网络现实**(团队在国内):代理隧道全线丢 UDP → Reactor 媒体改走 **TURN-TLS/443 TCP 中继**(SDK 只尝试首个 TURN 地址的缺陷已定位并绕过);全部 Lens M 流量走同一路径,内部严格可比;Xmax 走国内直连,与代理无关。

## 5. 已完成的实测结果

### 5.1 产品级首批数字 ⭐

| 测量 | 结果 | 条件 |
|---|---|---|
| **Xmax X2.0 官方通道(Lens P)** | **动作-上屏 p50 367ms / p95 633ms** | 合成录屏法,残差 ±1.9ms,640×360,25s,9 个闪光样本 |
| **Xmax X2.0 经 Reactor(Lens M)** | p50 1631–1695ms | 两批次 13 次运行 82 样本,批间差仅 64ms(互相印证) |
| **⇒ Reactor 平台开销(桥接)** | **约 1264–1329ms** | 同素材同分辨率双通道实测之差 |

**解读**:经 Reactor 访问时,时延的约 **78% 是平台开销**。这一数字目前基于单一模型(唯一双通道可达者),外推到其他模型合理但未经验证 —— 报告如实携带此保留。

### 5.2 平台地板校准(echo 空转模型,固定网络出口,漂移监测下)

| 条件 | 地板 p50 | 95% CI | 有效运行 | 真实故障 |
|---|---|---|---|---|
| C0 净网络 | 1928ms | 1894–1961(宽 66ms) | 40 | **0** |
| C0 轻负载 | 961ms | 928–961 | 40 | 0 |
| C2 (100ms/1%) | 1728ms | 1594–1828 | 24 | 2 (8.3%) |
| C1 / C3 | 待补测(验证器已修复) | — | — | — |

**三个要点**:
1. **地板不可做减法**:桥接交叉验证发现 echo(CPU 管线、软件编码)的地板**高于** GPU 模型的全程时延 —— 说明 echo 地板含 GPU 产品不承担的 CPU 编码成本。故 LingBot/Happy Oyster **不发布"模型净时延"**(数学上不可恢复),只发布同平台原始值+桥接开销作参照。宁可少一个数字,不发一个假精确的数字。
2. 地板与发送负载相关(两档负载差约 967ms,CI 分离)—— 任何对照必须负载匹配(桥接测量已按此钉死)。
3. 净网络下 **80 次运行 0 故障**:此前测得的"15–20% 平台故障率"确认为我方 VPN 隧道切换污染,平台无罪 —— 这也是我们把全部旧时延数据作废重测的原因(见 §6)。

### 5.3 生成类采集现状(如实)

- Happy Oyster:会话/指令协议已打通(create_world 文本导演模式);**世界生成为异步长过程**,首两轮采到的是"生成中"占位静帧 —— 内容分析当场识破(全片零帧间变化),判定作废、编码器污染实验的"合格"结论一并作废、门禁重新封锁。录制器已改为**画面持续动起来才开始录**(单次换图不再触发)。
- LingBot:需先上传种子图(i2v),完整指令序列已从官方 SDK 提取并实现;当日 GPU 池不稳(6 会话 5 次建联失败),该流程尚待一次完整验证。
- **结论:生成类采集是协议工程问题,路径已明,非阻塞性风险;但编码器污染实验可能最终需要实拍素材才能有效执行(生成内容若过于单一,考不动压缩差异)——若坐实,则 5 项门禁有 4 项系于拍摄。**

| 事故 | 系统响应 | 制度改进 |
|---|---|---|
| VPN 隧道在校准期间被切换,抖动冒充平台抖动 | 逐轮网络指纹比对发现;**全部受污染时延数据作废重测** | 网络漂移进入环境证据体系:漂移轮自动判 E;测量前固定出口成为标准程序 |
| Reactor 账户凌晨欠费(402) | 快速失败;欠费运行判 E**不进产品分母**(欠费是我们的问题不是产品的) | 校准工具接入预算闸;欠费即中止不再空烧尝试 |
| Reactor 服务端中途升级(版本戳捕获) | 数据按版本分段;同条件实测影响 ≤1 帧(33ms) | 版本逐 run 记录制度得到实战验证 |
| 采到"生成中"占位画面冒充素材 | 内容分析识破(零帧间变化);相关"合格"结论作废、门禁重锁 | 录制器加装"持续运动才开录"闸;逐环节人工目检留痕制度 |
| 中途进程被杀,弱网整形残留在系统上 | 恢复时探测发现并清除 | 整形施加/清除写入 finally;恢复程序首查残留 |

> 这些事故没有一个进入了最终数据 —— 每一次都被机制拦下、留痕、并转化为制度。这是"可辩护"的实际含义。
